# Implementation Plan: Body ECU bring-up

**Branch**: `001-body-ecu-bringup` | **Date**: 2026-10-14 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-body-ecu-bringup/spec.md`; technical context from `docs/spec-inputs/01-body-ecu-bringup.md`, Part B.

## Summary

Turn the CubeMX blink project into the layered firmware skeleton: a 1 ms cooperative scheduler with 1/10/100 ms slots, board support for LEDs, button and time base, and an ECU state module that runs a start-up lamp test, a 1 Hz heartbeat and a debounced button demo. Only the board's own LEDs and button are used. Pure logic is unit-tested on the PC.

## Technical Context

**Language/Version**: C11, arm-none-eabi-gcc (STM32Cube bundle 14.3.1 locally; Ubuntu `gcc-arm-none-eabi` in CI)

**Primary Dependencies**: ST HAL (STM32CubeF4, generated by CubeMX); Unity v2.6.1 for host tests (fetched by CMake)

**Testing**: CMake + CTest + Unity on the host (`tests/`), strict warnings (`-Wall -Wextra -Wpedantic -Wconversion -Werror`); flash-and-observe on the board

**Target Platform**: STM32F407G-DISC1, 168 MHz from 8 MHz HSE

**Constraints**: no dynamic memory, no blocking waits in `app/`, CubeMX files untouched except `USER CODE` blocks of `main.c`

**Scale/Scope**: 7 modules, about 7.5 KB flash, 1.6 KB RAM (Debug build)

## Design decisions

1. **Time base = HAL tick, read by polling.** HAL_Init already runs SysTick at 1 ms and counts in `HAL_IncTick()`. `bsp_tick_ms()` reads `HAL_GetTick()`, so the generated interrupt file stays untouched. *Alternative rejected:* a hook in `SysTick_Handler` would mean editing generated `stm32f4xx_it.c`.
2. **Scheduler counts whole ticks and catches up.** `sched_poll(now)` processes every missed millisecond one by one, so a late main loop (or a breakpoint) never shifts later periods: no drift by construction. Tasks run in the main loop, not in the interrupt. The time is a parameter, which makes the scheduler testable with a fake clock.
3. **Debounce is pure logic in `bsp/debounce.c`.** Counter-based: 5 stable samples at 10 ms = 50 ms, for press and release. `bsp_button.c` only reads PA0. Splitting the two keeps the HAL out of the tested code.
4. **ECU timing counted in 10 ms cycles.** Lamp test = 100 cycles, heartbeat half period = 50 cycles; exact to the tick, no clock reads in `functions/`.
5. **Debugger counters as `volatile` globals in their owning module**: `g_sched_uptime_ms`, `g_sched_task100_count` (sched), `g_ecu_state` (functions).
6. **Host fakes link instead of mocks.** `tests/fakes/fake_bsp_led.c` implements the `bsp_led.h` interface and records states.

## Project Structure

```text
ecus/body-zone-stm32/
├── Core/Src/main.c          # USER CODE: #include "app.h", app_init(), app_run()
├── CMakeLists.txt           # app sources + include paths
├── app/
│   ├── app.c/.h             # slot wiring: 10 ms → button sample, ECU state
│   ├── sched/sched.c/.h     # 1/10/100 ms slots, debugger counters
│   ├── functions/ecu_state.c/.h   # Init/Normal, lamp test, heartbeat, button demo
│   └── bsp/
│       ├── bsp_led.c/.h     # LED IDs → PD12–PD15
│       ├── bsp_button.c/.h  # PA0 sampling
│       ├── debounce.c/.h    # pure debounce logic
│       └── bsp_tick.c/.h    # HAL_GetTick wrapper
└── tests/
    ├── CMakeLists.txt       # Unity via FetchContent, one exe per module
    ├── fakes/fake_bsp_led.c/.h
    └── unit/test_debounce.c, test_sched.c, test_ecu_state.c
.github/workflows/firmware.yml   # host tests + target build on every PR
```

Call graph (downward only): `main.c → app → sched` and `app → functions → bsp → HAL`, `app → bsp`.
