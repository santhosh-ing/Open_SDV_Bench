01 · Architecture

Central HPC with zonal controllers

A central high-performance computer connects the cloud tier, the ADAS compute node, the instrument cluster and the zone controllers. The diagram shows each node with its board and the communication protocol of every link.

  • The central compute runs the vehicle gateway and owns the vehicle state.
  • Zone controllers keep safety-relevant behaviour local, so it survives a lost bus.
  • CAN, CAN FD, LIN and Ethernet are used where each medium fits.
  • Diagnostics are proven on top of the bench and are not its only purpose.

03 · Design principles

Design principles

01

Zone first

Functions that must survive a bus loss run in the zone. The turn indication is allocated fully to ZC01.

02

Fail-safe

If the vehicle state is missing for five cycles, ZC01 enters FAILSAFE. Hazard lights stay available in every state.

03

Single master

The gateway is the only source of the vehicle state. ZC01 has no manual mode switch.

04

Model-based

Eight viewpoints, from context to diagnostics, are kept as text so that they can be reviewed and compared by revision.

05

Traceable

No code without a requirement ID. No interface change without a model update and a decision record.

06

Update-ready

Parameter changes are applied only in the Update state, which prepares the bench for an over-the-air demonstration.

Vehicle state behaviour

Vehicle state and ZC01 failsafe

The gateway is the single master of the vehicle state: Off, On or Update. ZC01 follows this state. If the state message is missing for five consecutive cycles, ZC01 enters FAILSAFE and keeps the turn indication available locally. The simulation applies the rules of the decision record.

Decisions are recorded as ADRs

Each architectural decision is documented with context, options considered, decision and consequences, and is traced to the affected model views in the logical and physical architecture.

Turn indication allocated to ZC01

Acquisition, decision, blink generation and lamp driving run in the zone. ZC01 follows the vehicle state from the CGW and reports the indicator and hazard status to the central compute.

Options
Fully in ZC01 (chosen) · central decision in the HPC · split with the blink rhythm in the zone

Vehicle state management and failsafe

The CGW on the Raspberry Pi 5 is the only master of Off, On and Update. A dashboard sets the state through it. ZC01 has no manual mode switch and enters FAILSAFE after five missed cycles.

Options

05 · AI governance

System ownership stays with the architect

The system model is the control plane. AI works downstream of it and never upstream. Four decision levels define who decides what. When the level is unclear, the level with more control applies.

L0Architect only

Feature story, boundaries, requirements, architecture split and safety concept. AI does not propose a solution first.

L1AI advises

Interfaces, technology choices and test strategy. The architect drafts, AI challenges, the architect decides and records an ADR.

L2AI drafts

Core embedded code. Every line is reviewed and can be explained by the architect.

L3AI executes

Boilerplate, build scripts and CI. Review through a diff summary and passing tests on hardware.

Traceability chain Feature story → Requirement (StrictDoc ID) → Model view → Interface (DBC / VSS / API) → Code → Test → Evidence on hardware

Working loop per feature slice

  1. Intent Sketch and rough interface, written without AI support.
  2. Challenge AI identifies gaps, risks and alternatives.
  3. Decision Recorded as an ADR.
  4. Model and requirements Affected views and IDs are updated.
  5. Implementation Small slices with an approved plan.
  6. Review Diff of about 200 lines or less, then explain-back.
  7. Verification Expected behaviour is written down before running on hardware.
  8. Close Commit with IDs and a session log entry.

A milestone is complete only when the affected views are updated. Views are kept as text in the repository.

Why the charter exists

  • Control. Every architectural decision is made by the architect and written down.
  • Learning. AI must extend the architect's capability and not replace it.
  • Explainability. For every part of the bench the architect can state what it does, why this design, which alternatives were rejected, how it fails and how it was verified, without AI.

Hard rules for AI

  • AI never changes requirements, model views or interfaces without explicit approval.
  • AI never touches files outside the stated scope of the task.
  • AI states assumptions and open questions instead of silently guessing.
  • Plan before code, small diffs, one concern per change.
  • No new dependency or framework without an ADR.
  • If AI disagrees with the design, it says so. Challenge is wanted, not compliance.

Learning safeguards

  • Learn zone and delegate zone. In the learn zone the architect writes the first version and AI reviews.
  • Predict before run. Expected behaviour is written down before flashing.
  • Explain-back. AI code is merged only after the architect explains it in own words.
  • Tutor mode. AI teaches and asks questions instead of giving the full answer.
  • Learning log. Three lines per session: learned, unclear, to read next.
  • Monthly whiteboard check. Topology, signal flow and one diagnostic sequence are drawn from memory.
Single source of truth

The repository

The repository is authoritative, not the chat history. Every decision from a discussion lands as an ADR or requirement before implementation starts.

Thinking room

Claude chat

Architecture discussion, trade-offs, learning and review.

Workshop

Implementation against approved ADRs and requirements. A CLAUDE.md in the repository carries the hard rules, and both tools read the latest session log at the start.

From code to blinking LED: the pipeline

  1. Describe the hardware setupSTM32CubeMX generates the clock, pin and peripheral initialisation.
  2. Write the application codeProject code lives in app/, separate from generated files.
  3. Plan the buildCMake describes sources, flags and target.
  4. Compile and linkNinja drives arm-none-eabi-gcc and produces the .elf.
  5. Flash it to the chipST-LINK over SWD writes and verifies the image.
  6. The chip bootsReset vector, start-up code, clock set-up, then main().
  7. Your code runsapp_init() once, app_run() in the main loop.
  8. Observe and verifyDebugger watch, LEDs and later the CAN bus confirm the behaviour.

1. Introduction and goals

A desktop software-defined-vehicle bench that demonstrates a realistic SDV architecture: a central vehicle computer with Eclipse SDV components (Kuksa Databroker + VSS, Eclipse OpenSOVD, Ankaios), zone controllers on CAN, CAN FD and Ethernet with a LIN sub-bus, an instrument cluster, an ADAS domain, and a cloud backend for OTA and remote diagnostics. Quality goals: traceability, modularity, runnable without hardware (virtual twins).

2. Constraints

Hobby hardware (STM32F407G-DISC1, Raspberry Pi 5, Arduino, Jetson Orin), open-source software only, CAN classic at 500 kbit/s and 100 Mbit Ethernet.

3. Context and scope

To be completed (M0 issue "Diagram: system context").

4. Solution strategy

Contracts first, spec-driven development (Spec Kit), layered firmware (ADR 0001), command/status CAN split (ADR 0002), central HPC star with CAN and Ethernet links and a cloud tier (ADR 0003), virtual twin per ECU.

5. Building block view

Body zone ECU firmware layers: see the software view and ADR 0001.

6.–12. Runtime, deployment, concepts, decisions, quality, risks, glossary

Filled in as the milestones progress.

Network / topology view

Physical view of the bench: which nodes exist, how they are connected and which protocol runs on each link. The editable draw.io source is network-topology.drawio.svg; the animated diagram above is the interactive version.

Topology

A central HPC star: the Raspberry Pi 5 is the hub. Every zone controller and domain computer has one link to it, and the cloud connects through it. A zone may own a sub-bus below it (LIN below the rear zone). Each link uses the medium that fits its job:

  • Ethernet / IP where services, containers or larger data are exchanged (cloud, ADAS, sensor zone).
  • CAN where a small, deterministic, cyclic signal set and classic diagnostics are needed. The HPC drives two buses: the classic body CAN (front body zone, door module) and a CAN FD bus (rear body zone).
  • LIN for low-cost smart sensors and actuators below a zone controller.

Open points

  • Arduino model: decides whether an Ethernet shield (e.g. W5500) is needed and how much protocol fits into its RAM.
  • Ethernet ports: the Pi 5 has one. Either a small unmanaged switch is added, or the cloud link uses the Pi's Wi-Fi (preferred, mirrors the vehicle's cellular uplink).
  • Protocols per link are planned, not final. Each is confirmed by an ADR when its milestone starts.
  • ADR 0008 open points: rear indication in step across two zones, cluster link and role, door link, key security, LIN node function.
  • MCP2515 is classic CAN only: it fits the body CAN, not the CAN FD bus.

Requirements

Managed as text files with StrictDoc (ADR 0004). Each requirement is an object with a stable ID, attributes and links, versioned in git and checked by CI on every pull request. 50 requirements at the time of this snapshot.

Hierarchy

FileLevelID schemeVerified by
00-stakeholder-needsStakeholder needs (8)STK-NNNDemonstration on the bench
10-system-requirementsSystem, vehicle level (14)SYS-<AREA>-NNNSystem tests on the bench
20-function-requirementsLogical functions, node-independent (10)FUN-<AREA>-NNNIntegration tests (HPC + virtual twins)
30-zc-stm32-requirementsComponent: body zone controller (18)SW-ZCS-NNN, HW-ZCS-NNNHost unit tests, tests on the board

Later component files: 31-hpc, 32-zc-arduino, 33-adas, 34-cloud, and for ADR 0008 nodes 35-zc-s32k, 36-lin-mcxa, 37-cluster, 38-zc-door. Areas: LIGHT, SAFE, DIAG, ARCH, VEH, ACC, HMI.

Link rules (tools/req_check.py)

  • SYS → parent STK; FUN → parent SYS; SW/HW → parent FUN (constraints may trace directly to SYS).
  • Every requirement below STK has at least one parent.
  • Allocation to a node happens at component level (ALLOCATED_TO). A function without component children is reported as "not yet refined", which makes open allocation decisions visible.

Attributes

FieldMeaning
UIDStable ID, never reused, never renamed
STATUSDraft → Agreed → Implemented → Verified, or Obsolete
KINDFunctional, Non-functional, Constraint
ALLOCATED_TOZC-STM32, HPC, ZC-Arduino, ADAS, Cloud, ZC-S32K, LIN-MCXA, Cluster, ZC-Door
VERIFICATIONTest, Demonstration, Inspection, Analysis
MILESTONE · RELEVANCE · LEGACY_IDOptional: M1 to M8; Safety / Security; former ID of migrated requirements

Writing a requirement (EARS)

PatternTemplate
UbiquitousThe <system> shall <response>.
Event-drivenWhen <trigger>, the <system> shall <response>.
State-drivenWhile <state>, the <system> shall <response>.
Unwanted behaviourIf <condition>, then the <system> shall <response>.

Change process

  1. Change by pull request onlyEdit the .sdoc files or use the StrictDoc web editor, then open a PR with reason and impact.
  2. CI validatesSyntax, unique IDs and links (StrictDoc) and the project rules (req_check.py).
  3. Review suspect linksIf a title or statement changes, CI lists the children as warnings.
  4. Never deleteSet STATUS to Obsolete so old reports and commits stay traceable.
  5. Status follows evidenceImplemented or Verified only with a test carrying @verifies <ID>.
  6. BaselinesGit tags on main, e.g. req-baseline-M1.
