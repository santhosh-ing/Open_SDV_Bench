# AGENTS

Single source of rules for every AI coding assistant working in this repository (Claude Code, Codex, Copilot, …). `CLAUDE.md` points here.

## Project

**Open SDV Bench** is an open-source desktop software-defined-vehicle bench: a central vehicle computer (Raspberry Pi 5) running Eclipse SDV components (Kuksa Databroker + COVESA VSS, Eclipse OpenSOVD, later Ankaios), connected to an STM32 body zone controller over CAN, an Arduino sensor zone controller and an ADAS domain (NVIDIA Jetson Orin) over Ethernet, and a cloud backend (OpenSDV.Cloud) over IP. Topology: ADR 0003. It is developed with systems-engineering discipline: requirements, architecture, decisions and traceability are first-class.

The maintainer is a systems architect, not a professional programmer. Explain non-obvious embedded concepts briefly in comments or plans.

## Rules

### 1. Contracts first (non-negotiable)
- Files in `interfaces/` are contracts and are written before the code that implements them.
- A contract changes only together with an ADR in `docs/adr/` and a version bump inside the contract file.
- Never hard-code CAN IDs, bit positions, scaling or signal values. CAN pack/unpack code is generated from the DBC with `tools/gen_can.sh` into `app/com/generated/` and is never edited by hand.

### 2. Traceability
- Requirements live in `docs/requirements/*.sdoc` (StrictDoc, ADR 0004). IDs: `STK-NNN`, `SYS-<AREA>-NNN`, `FUN-<AREA>-NNN`, `SW|HW-<NODE>-NNN` (e.g. `SW-ZCS-021`). Never reuse or delete an ID; set `STATUS: Obsolete` instead.
- Change requirements only in a pull request; run `python3 tools/req_check.py` before committing. Never invent requirement IDs in code or specs; add the requirement first.
- Specs name the requirement IDs they implement. Tests carry `@verifies <ID>` for every requirement they verify (spec FR numbers may be named in addition).
- Set a requirement to `Implemented` or `Verified` only when a test with `@verifies <ID>` exists.
- Commit messages reference the spec number and/or requirement ID, e.g. `spec-002: command timeout (SW-ZCS-021)`.

### 3. Firmware layering (`ecus/body-zone-stm32/`)
- `Core/`, `Drivers/` and the `.ioc` file are generated by STM32CubeMX. Never edit them by hand, except inside `USER CODE BEGIN/END` blocks of `main.c`, and only to call `app_init()` once and `app_run()` in the main loop.
- All project code lives in `app/`. Layers call downward only:
  - `functions/` — vehicle functions (hazard, indicators, low beam, mirror). Pure logic, **no HAL calls**.
  - `com/` — CAN driver wrapper, generated DBC code, cycle times, timeouts, alive counters.
  - `diag/` — UDS server (milestone M3).
  - `bsp/` — LEDs, button, servo. Only `bsp/` and `com/` may call the ST HAL.
  - `sched/` — cooperative scheduler, 1 ms tick.
  - `test_stim/` — loopback-only test stimulus, compiled only with `BODY_CAN_LOOPBACK`.
- Host unit tests live in `ecus/body-zone-stm32/tests/` (CMake + CTest + Unity) and run without hardware.

### 4. Determinism and safety mindset
- No dynamic memory allocation in firmware. No blocking waits in application code (`HAL_Delay` only in generated init code).
- Validate every received CAN frame (ID, DLC, alive counter) before use.
- Every input has a defined fail-safe on loss, reported on the bus. Explicit ECU states: Init, Normal, Degraded, Fault.

### 5. Small, hardware-verifiable increments
- One feature in progress at a time. Each feature fits in one evening of implementation plus verification on the board.
- Every task list ends with explicit "flash and observe" steps. Ideas outside the current spec go to a GitHub issue labelled `parking-lot`.

### 6. Virtual twin parity
- Once a physical ECU has a twin in `ecus/virtual/`, every behaviour change is applied to both and the same integration tests run against both.

### 7. Code style
- C11, `<stdint.h>` types, `static` for everything not exported, named constants instead of magic numbers, MISRA-C-inspired (no compliance claim).
- Every module starts with a header comment: purpose, layer, spec and requirement IDs.

## Hardware facts: body zone ECU
- Board **STM32F407G-DISC1**: MCU STM32F407VGT6, Cortex-M4F up to 168 MHz, 8 MHz HSE crystal, on-board ST-LINK.
- LEDs: LD4 green PD12, LD3 orange PD13, LD5 red PD14, LD6 blue PD15. User button B1 on PA0 (active high).
- Lamp mapping: green = left indicator, red = right indicator, orange = low beam, blue = ECU heartbeat.
- CAN: on-chip bxCAN (CAN1, CAN2). No transceiver yet → silent loopback mode. Check pins against UM1472 before wiring.
- Toolchain: STM32CubeMX + STM32Cube for VS Code, CMake, arm-none-eabi-gcc, ST HAL.

## Workflow
- Spec Kit: `/speckit-constitution` → `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` → maintainer verifies on hardware.
- One branch per spec (`NNN-feature-name`), merged into `main` via pull request.
