---

Create the constitution for **open-sdv-bench**, an open-source desktop software-defined-vehicle (SDV) bench. It shows a realistic automotive E/E architecture on hobby hardware: zone ECUs (STM32, Arduino) on CAN, a central vehicle computer (Raspberry Pi 5) running Eclipse SDV components (Kuksa Databroker with COVESA VSS, Eclipse OpenSOVD), and an ADAS domain (NVIDIA Jetson Orin). The project is developed with systems-engineering discipline: requirements, architecture, decisions and traceability are first-class. The maintainer is a systems architect, not a professional programmer — code must be readable and explained.

## Core principles

### I. Contracts first (NON-NEGOTIABLE)
- Everything in `/interfaces` is a contract: `interfaces/can/*.dbc` (CAN matrix), `interfaces/vss/` (signal model), `interfaces/diag/` (diagnostic description).
- Contracts are written and reviewed BEFORE the code that implements them.
- A contract may only change together with an Architecture Decision Record in `docs/adr/` and a version bump in the contract file.
- Code never hard-codes CAN IDs, bit positions, scaling or signal values. CAN pack/unpack code is GENERATED from the DBC (cantools `generate_c_source` for C, cantools for Python) and committed under a `generated/` folder that is never edited by hand.

### II. Traceability
- System requirements live in `docs/requirements/` with IDs `REQ-<AREA>-<NNN>` (e.g. REQ-BODY-001).
- Every feature spec states which REQ IDs it implements. Every test states which requirement (REQ or FR) it verifies.
- Commit messages reference the spec number and/or REQ ID.

### III. Layered firmware architecture
For every microcontroller ECU (first: `ecus/body-zone-stm32/`):
- Code generated by STM32CubeMX (`Core/`, `Drivers/`, the `.ioc` file) is never edited by hand, except inside the `USER CODE BEGIN/END` blocks of `main.c`, and only to call `app_init()` once and `app_run()` in the main loop.
- All project code lives in `app/`, in layers that may only call downward:
  - `app/functions/` — vehicle functions (hazard, indicators, low beam, mirror). Pure logic, no HAL calls.
  - `app/com/` — CAN communication: wraps the HAL CAN driver, uses the generated DBC code, handles cycle times, timeouts and alive counters.
  - `app/bsp/` — board support: LEDs, button, servo. The only layer (besides com) allowed to call the ST HAL.
  - `app/sched/` — cooperative scheduler (1 ms tick, fixed task periods).
  - `app/diag/` — UDS diagnostics (later milestone).
- Vehicle functions communicate with com/bsp through small, explicit C interfaces (header files), so the same function logic can run in the virtual twin and in host unit tests.

### IV. Determinism and safety mindset
- No dynamic memory allocation (no malloc/free) in firmware.
- No blocking waits in application code (`HAL_Delay` is forbidden outside of CubeMX-generated init code). All timing via the scheduler tick.
- Every received CAN frame is validated (ID, DLC, alive counter) before its content is used.
- Every input has a defined fail-safe behaviour on loss (timeout), and the fail-safe state is reported on the bus.
- Defined ECU states (Init, Normal, Degraded, Fault) with explicit transitions.

### V. Small, hardware-verifiable increments
- Each feature is small enough to be implemented, flashed and verified on the real board in one evening.
- Every task list ends with explicit "flash and observe" verification steps describing what the maintainer must see on the board (LED patterns, debugger values).
- Pure logic (functions, signal handling) also gets host-side unit tests that run on a PC without hardware (CMake + CTest, Unity test framework).

### VI. Virtual twin parity
- Each physical ECU will get a Python virtual twin (`ecus/virtual/`) on virtual CAN, using the same DBC and diagnostic description. Once a twin exists, every behaviour change must be applied to both, and the same integration tests run against both.

### VII. Readable, explained code
- Language for firmware: C11 with fixed-width integer types (`<stdint.h>`), `static` for everything not exported, no magic numbers (named constants), MISRA-C-inspired style without formal compliance claims.
- Every module has a header comment: purpose, layer, which spec/requirements it implements.
- The agent explains non-obvious embedded concepts briefly in comments or in the plan, because the maintainer is learning embedded development.

## Hardware facts (body zone ECU)
- Board: STM32F407G-DISC1 (MCU STM32F407VGT6, Cortex-M4F, up to 168 MHz, 8 MHz HSE crystal, on-board ST-LINK for flashing/debugging).
- User LEDs: LD4 green PD12, LD3 orange PD13, LD5 red PD14, LD6 blue PD15. User button B1 on PA0 (active high).
- CAN: bxCAN controllers CAN1 and CAN2 on-chip. No CAN transceiver is connected yet, so early features use silent loopback mode. Pin assignment must be checked against the board user manual (UM1472) before the transceiver milestone.
- Toolchain: STM32CubeMX (+ STM32Cube for VS Code extension), CMake, arm-none-eabi-gcc, ST HAL.

## Development workflow
- Spec-driven: `/speckit-specify` (what & why) → `/speckit-clarify` → `/speckit-plan` (how) → `/speckit-tasks` → `/speckit-implement` → verification on hardware by the maintainer.
- One feature in progress at a time. Ideas outside the current spec go to a GitHub issue labelled `parking-lot`.
- Work happens on a feature branch per spec, merged to `main` via pull request.

## Governance
- This constitution takes precedence over plans, tasks and agent habits. When a plan conflicts with it, the plan changes.
- Amending the constitution requires an ADR and a version bump of this file.
